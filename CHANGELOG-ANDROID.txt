CHANGELOG OF THE SUPER MARIO RPG PORT FOR ANDROID (smrpg-recomp-android)
========================================================================
Newest first. Numbering x.y.z-alpha / x.y.z-beta (Semantic Versioning, like the Windows port): alpha as long as the game
can't be played from start to finish on Android, beta after that (versions up to 0.9.0 were named -alfa). The APK carries
this version (tools/android/apk.sh: versionName; versionCode = x*10000 + y*100 + z).
Base: the Windows port 0.48.0-beta (https://github.com/ElKiro1311/smrpg-recompiled; CHANGELOG.txt has its history up to
there).

0.8.11-alfa (2026-11-20) — the vertex cache without OS tracking: shadow comparison
  0.8.10 relied on the OS's per-page write tracking (GetWriteWatch on Windows, uffd or PAGEMAP_SCAN on Linux)… and the
  Thor has neither ("[vk] no page write tracking (-1, page 4096)": no userfaultfd and no PAGEMAP_SCAN): the cache stayed
  off and the excess upload remained. Now, without tracking, the cache goes by SHADOW COMPARISON: each entry keeps its
  own copy in RAM, and each present compares page by page (memcmp) and copies to the GPU only the pages that changed; if
  there's no memory for the shadow, no entry is made (the usual copying); pages written by the GPU are still excluded
  (the marks from the shaders' stores work without the OS); teardown frees the shadows. LARECOMP_VK_VCACHE still has the
  last word. MEASURED on the Thor (Mushroom Way, its fsr1/smaa/1x/60 settings): the same scene uploaded 13.9 KB per draw
  without the mode and 10.5 KB with it (−24%): the static part (the terrain) is saved, while whatever the game rewrites
  every frame (animated meshes, constants) is still uploaded. A steady 60 fps, GPU at 475 MHz with no throttling
  (thermal_pwrlevel 0), until the usual thermal shutdown. And a "flicker" was rechecked with the same game settings:
  110 s cold + 170 s at the thermal limit, recorded at 30/s — not a SINGLE drop in sharpness outside the game's own
  loads/menus/transitions, and the clues in its log (the four "[pace] resolution setting changed" and the two SMAA
  stencil sizes) are just changes made in the menu (pace.c confirms it); which area it happens in is still to be found
  out.

0.8.10-alfa (2026-11-20) — the excess upload: vertices and indices through the page cache, not copied every frame
  The problem, measured: the Thor uploaded ~334 MB/s at 60 fps (667 MB every 2 s, ~20 KB for each of the window's 32,670
  draws) and the S23 ~470 MB/s (~11 MB per frame). The cause: on the Adreno the game's heap can't be imported as a
  Vulkan buffer ("lazy heap import: not possible here (no host memory import)"), so every vertex, index and constant
  landed in the transient ring AND WAS COPIED AGAIN EVERY FRAME (guest_copy's cache only lives within one present). The
  PC doesn't suffer from this: it imports the heap (its draws go direct; its ~15 MB/frame upload is the per-draw
  constants, already covered by the present's dedupe). The fix: the vertex page cache (vcache_lookup, with the OS's
  per-page write tracking) already existed for this case but was only consulted on the import path, which Android
  doesn't have — now a vertex or index miss consults it before copying: the first frame copies the whole range and the
  following ones only the pages the OS saw written; pages written by the GPU are excluded (skinning), and without
  tracking or with the cache off the usual path remains. LARECOMP_VK_VCACHE=0/1 still has the last word. Verified on PC
  (hidden): identical (same 1,899 MB/2 s upload, 0 cache hits since it goes direct there, screenshot with a diff of 0.4
  and 0/880 blocks against the baseline). STILL TO BE MEASURED on the Thor and the S23 once they're available: upload
  before/after, fps, temperature and GPU frequency (devfreq/cur_freq, gpu_busy_percentage).

Sweeping and pre-translating the ~82,000 shaders on the Thor (2026-11-20) — studied with a sample: NOT WORTH IT
  The idea: run tools/shader_sweep.c (which links the runtime's own translator and compiles to SPIR-V with shaderc) over
  the RomFS packages, in batches and in the background on the Thor, so that anything never seen before arrives already
  translated. Real sample on PC (300/package over shaders/pkg): 672 shaders in 2.35 s = 286/s single-threaded, 13
  translation failures (3 unknown opcodes, ~2%). Extrapolated: ~82,000 in ~5 min on PC, or ~48 s on the Thor with
  0.8.2's pool of 6 (plus a session's worth of heat); the cached SPIR-V would take up some 250-400 MB. BUT the split
  measured in the first-visit storms kills it: the castle = 4-8 PROGRAMS translated versus 216 PIPELINES created by the
  driver (worst frame 366 ms; battles: 140 on the Thor, 289 on PC). Translation — the only thing the sweep saves — is
  milliseconds, already parallelized; the black flash lives in the driver's 216+ creations, which are shader × STATE
  (blends, formats the game picks while playing): they can't be pre-derived from the packages, and the pipeline cache is
  GPU-specific — the PC can't donate its own to the Adreno. Pre-translating everything would attack the cheap part. What
  does attack the expensive part: warming up the driver's cache ON the console by creating the real pipelines, and that
  already exists: LARECOMP_SHADER_TOUR (warping through every warp spot compiles them and leaves them in
  vk_pipelines.bin) — hours of play on the console, a separate decision. Idea noted and ruled out by the numbers.

Robustness tests (2026-11-20, after 0.8.8)
  1. LONG SESSION (30 min planned; the thermal ceiling rules): at continuous 1080p the chassis (xo) hits the watchdog's
  limit (55 °C) in ~7-10 min depending on the starting temperature, even though the CPU no longer gets near its cutoff
  (75 °C where it used to be 95). Delivered as a 7 min slice with RSS every 30 s (long_session.sh): NO LEAK — RSS starts
  at 2.78 GB, loads up to 3.10 GB and then the increments SHRINK (+2.7 MB/min → +0.2 MB/min: the working set settling,
  not the linear signature of a leak); 60.0 fps from start to finish (the only dip, the startup ramp), 0 Vulkan errors,
  0 skipped draws. (A continuous 30 min session is physically impossible with the thermal protection: that is itself
  part of the result.)
  2. LIFECYCLE (lifecycle.sh): 10 times to the background (Home) and back — the task returns to the front, and the
  process and rendering survive all 10 cycles (constant pid, clean final screenshot, 0 errors) — and the screen off and
  on 3 times, same result. Unplugging and replugging the controller can't be simulated over adb: left untested.
  3. SAVING THE ROUGH WAY (save_and_cover.sh): the remake only writes the save when you TOUCH a save block — neither
  walking (60 s right, 60 s left, 7 min back and forth with battles) nor fighting triggers the autosave (the save's md5
  intact in all of them), and the block can't be reached blindly with scripted input. What was verified: a brutal
  force-stop mid-game ×3 — a clean reload EVERY time (60 fps in the field, 0 errors, in-game screenshot), and the
  player's save (written by the game itself) loads on every boot. Left to test by hand (10 s): touching a save block and
  closing right after — the fresh write against the force-stop.
  Scripts added to the repo (tools/android/): long_session.sh (RSS per minute + monitoring), lifecycle.sh,
  save_and_cover.sh. No degradation of the game found: no fix to cut a version for.

0.8.8-alfa (2026-11-20) — ui_run's loop per platform (correction to 0.8.7); audio-out no longer polls
  1. (correction) The new window loop was the default everywhere, and on PC SDL_WaitEventTimeout really sleeps and wakes
  up as each event arrives: better latency than a fixed 16 ms cadence at 120-240 fps. Now Android uses the new one (main
  thread at 0.4%) and the other platforms the per-event wait; LARECOMP_UI_SPIN=0/1 forces either one on any platform.
  Verified on PC (hidden): f01out at 60 fps, 0 errors, scripted input working; Thor: same thread map as 0.8.7 (148%).
  2. The audio output thread no longer polls the queue every 1 ms when there's nothing in it: it waits on a condition,
  woken when a buffer is queued and also on Start/Stop and at shutdown (without that last signal the join would hang).
  In normal play it stays at 1.4%: that's the real rate at which it releases the buffers, by design (releasing them
  instantly would be a hot loop in the game's own audio thread). What's gone is the dead polling BETWEEN sessions
  (menus, loads): a thousand wakeups per second for nothing.
  3. Measured on the Thor (f01out standing still, hilos_thor.sh with names): total CPU 148% (0.8.7: 151%), main thread
  out of top's list (<0.8%), audio-out 1.4% with playback running. (An 82% that shows up ONLY in the first session after
  reinstalling the APK is a startup transient: it isn't there in the following ones.)
  4. And the remaining CPU use, measured and closed: turning the recorder off (LARECOMP_VK_RECORDER=0, the Vulkan calls
  on the draw thread itself) gives EXACTLY the same (148% versus 148%; rqueue 24% + recorder 18% separate = 40.2%
  merged): the ring has no net cost and the two-thread pipeline buys parallelism — it stays. guest-main (50%) is the
  game itself (41k function calls per frame) on the generated C (the translator's c->x[] register file: its multiplier
  is the GENERATOR's business, not the runtime's); rqueue/recorder (24/18%) are its 713 draws per frame. On the runtime
  side, exhausted.

0.8.7-alfa (2026-11-20) — half the heat: the main thread no longer spins on Android
  With the game idle at 1080p, the Thor used 253-343% CPU (top -H) and the CPU reached 95 °C in two minutes (the
  watchdog cut the session short). The per-thread map — hilos_thor.sh, now with each thread's name (/proc): the runtime
  now names its threads (plat_thread_name: guest-main/guest-N, vi-vsync, rqueue, recorder, shader-prep, seen-writer,
  shader-trans/build, cache-saver, audio-ren/out, disp-watch, hang-watch) — gave the culprit away: the app's MAIN thread
  at 99.8% (a third of the heat), with the game doing nothing. It was ui_run's loop (device.c):
  "SDL_WaitEventTimeout(&e, 16)" doesn't sleep on Android — it spins. Now the loop collects the pending events in one go
  (PeepEvents), does its periodic work and really sleeps until its next tick on the runtime's timer. Input loses nothing
  noticeable: the game reads it once per frame. LARECOMP_UI_SPIN=1: the old loop, for comparison.
  Measured (same 120 s run from cold): main thread 99.8% → 0.4%; total CPU 253-343% → 151%; the rest is real work
  (guest-main 50%, rqueue 24%, recorder 18%); CPU 63→95 °C before → 60→77 °C after (no longer anywhere near the cutoff);
  xo +16.8 before → +10.7 after over 120 s; 60 fps intact (median 60, better minimum).
  Residual, noted: audio-out 1.4% even with LARECOMP_NO_AUDIO=1 (it releases buffers at its own pace; minor).

0.8.5-alfa (2026-11-20) — hitches: the mechanism, settled for real (and the last runtime fix, measured and ruled out)
  1. The game's GPU counters are DORMANT in normal play: a 2,500-frame window with LARECOMP_FNPROF (6,132 functions
     counted) and the counter's entire family (the initializer 0x70010c4c24, the getter 0x70010c51f0, its vtable
     trampolines 0x70010c1exx: zero entries). The "the controller reads renderer+0x81c0" story belonged to the Link
     game: in SMRPG that path doesn't run and the drop doesn't come from there. (The name "f_700000c910" in the
     pace.c/patches.py notes is Link's; SMRPG's 7001'… ones really are its own.)
  2. The hitch's signature, measured cleanly: the game's frame floats within ±1-5.5 ms of its own clock, and when it
     lands past a vsync tick it waits ONE WHOLE REFRESH and presents on the next one (a "+2" in [pacing]; the controller
     in 30 mode during that frame). In the field: 3 pure tick misses in 5,307 frames (tirones-pace) ≈ one every 29 s —
     exactly 0.7.7's cadence. The other "+2"s are the game's own 21-400 ms frames (loads and startup: there 30 is
     right). During the hitch the ENTIRE runtime is idle (game CPU 0.7-1.6 ms, real GPU 2-3 ms, pacer with nothing
     late): the game misses the deadline all by itself, on correct data. The runtime is no longer feeding it anything
     wrong.
  3. Tried and ruled out, with numbers (built, run, reverted): (a) a grid at the panel's REAL rate — measured from 6,556
     pairs of presents: 16.6530 ms on average (the driver says 16.6667; −0.082%; crossings every ~600 frames) — the
     average game↔vsync drift fell from 0.08% to 0.002%... and the tick misses stay the same (5 in 5,300, versus 3
     before); (b) the same + vsync events 4 ms BEFORE the grid (the game's jitter would land inside the tick): first run
     0 misses in 5,137, second 4 in 4,855 — the same binary; thermal swings dominate and the improvement doesn't hold
     up. The panel's rate really was off and the pacer now knows how to measure it (the recipe is below); but the game's
     hitch doesn't come from there.
  4. What's left to try, if it's ever to be killed off for good: the hle_override hook (movie_fit.c's pattern) on the
     game's controller, so that a one-frame miss doesn't drop it to 30 (it's an internal decision of its own, on data
     that's served correctly: it means touching its code, not the runtime). Or accept it as the game's own: its ±1-5 ms
     of jitter per frame with the CPU at 95 °C is the ultimate cause and couldn't be reduced from the outside.
     (Measurement recipe, in case it's reused: LARECOMP_VK_PACING_LOG gives the [pacing] p/d lines; the "pure tick
     miss" = a g_vsync step >25 ms with the game's frame <25 ms; the real refresh = the mean of the gaps between the
     [pacing] p lines within an 8-25 ms band.)

0.8.4-alfa (2026-11-20) — 28-38 ms hitches every 30-40 s: avenue explored and ruled out (the numbers remain)
  1. The hitches are the game's own controller dropping to its 30 mode for ONE frame: its main thread waits 2 vsyncs and
     comes back. Measured in f01out while walking (LARECOMP_LOG_PACE + raw [pacing]): in every hitch the entire runtime
     is idle — game CPU 0.7-1.6 ms, render ≤1 ms, real GPU 2-3 ms, pacer with no late presents (17-25 ms margins),
     SyncWait immediate — and the frame before the drop is normal too (period 15.6-17.1).
  2. Ruled out with the numbers: Unity's GC (the 15 frames with the most game-thread CPU out of 7,200 are startup and
     loading artifacts: none of them periodic); cache saving and the log (no I/O in the frame); the GPU frequency (a
     steady 615/680 MHz, no drops); the NVN counter query (SMRPG doesn't use ReportCounter: that's the Link game's, and
     the renderer+0x81c0 counters its controller does read don't come from there); and present pacing: building the grid
     with the panel's REAL period measured from the presents was tried, and the "control" itself ruled it out — the
     actual presents (actualPresentTime) don't measure the panel's clock but the compositor's close-out (14.8 ms on
     average at 60 fps on the Thor, jumpy); with that grid the pacer disqualifies itself ("not whole refreshes") and the
     game runs WITHOUT present pacing... and the hitches stay the same (4 in ~90 s, same as with it). The game's vsync
     clock measured a median of 16.6422 ms (0.147% fast) because its anchor is those same presents: it's the compositor
     that's out of step with the panel, not the other way around. Reverted, no code committed.
  3. Next lead (so as not to start over): the controller decides on something the runtime doesn't instrument yet. Still
     to be looked at: the count of vsync events the game consumes (the signal from vi.c's thread may coalesce if the
     game re-arms its event late: it would read a skipped tick) and its internal counters at renderer+0x81c0 (who fills
     them, with what clock — fnprof with the window on a hitch). Not the GC, not the caches, not the log, not
     presentation: no need to look there anymore.

0.8.2-alfa (2026-11-19) — new areas: fewer silhouettes and a shorter worst frame (more build threads)
  1. When entering a never-seen area, the draws whose pipeline is still compiling are skipped (the silhouettes) and
     there's one long frame; both depend on how many threads compile at the same time. It was "cores - 4" (4 on the
     8-core Thor); now it's "cores - 2" (6 on the Thor), minimum 4, and LARECOMP_BUILD_THREADS=N sets a fixed number
     (docs). Measured entering the same never-seen castle three times, with the same load all three times (216 compiles)
     and the game alive at the end:
     - 4 threads: 1312 skipped draws and a 456 ms frame;
     - 6 threads: 987 skipped (-25%) and a worst frame of 366 ms (-20%);
     - 8 threads: 1395 skipped and present pacing broken for ~10 s (291 frames in a row at 33 ms on screen, even though
       the game stayed at 60): the game's threads, the draw thread and the translator eat CPU too, and there's none to
       spare for presenting on time. 6 threads is the sweet spot: it cuts the skipped draws without throwing anyone off
       pace.
  2. Bringing over to the Thor what's already been seen on PC (without touching code): the PC runs the scene with
     LARECOMP_VK_DYN_DEPTH=0 (depth fixed in the pipeline, as on the Adreno; without that its lines come out without
     " z=" and are no good), and the new lines of its own list and whatever codes are missing are copied to the Thor (by

0.7.7-alfa (2026-11-19) — At 60 fps, the display at 60 Hz: the remaining hitch is gone
  1. The hitch that remained at 120 Hz (one every ~4 s in 0.7.6) was Android's compositor, as seen in a system trace
     (atrace): at 120 Hz it starts composing each frame only 1.85 ms before the refresh it shows it on, and the
     submission to the top screen's panel (Qualcomm's display service and the kernel) has to get there at least about
     0.7 ms before the vsync. It gets there with 0.2-0.4 ms to spare; when the validation or the submission takes a bit
     longer (0.9-1.4 ms instead of 0.25), the kernel leaves the frame for the next refresh. The game can't speed up the
     compositor, but it can ask the display for its own rate: at 60 fps it now asks for 60 Hz
     (ANativeWindow_setFrameRate), and at 60 Hz the compositor starts about 15 ms before the refresh: no more race
     ("On Time Present"). Measured on the Thor (5 minutes of walking, 1080p, SMAA): 99.96% of the frames at 16.7 ms
     (0.7.6: 99.1%; before 0.7.6: 91.6%); what's left is the game's own hitches (one frame with 28-38 ms of CPU every
     30-40 s). In exchange, it takes about 10 ms longer from when the game presents a frame until it's seen (35 versus
     26 ms).
  2. With Lossless Scaling frame generation it asks for the resulting rate (the pace times the multiplier: 120 Hz with
     x2; with x3 or x4, Android sets the highest). Withdrawing the request wasn't enough: the Thor stayed at 60 Hz and
     generation couldn't get its frames out. With "FPS limit" at 120 or 40, 120 Hz; at 30, 60 Hz. Android goes back to
     its own rate when leaving the game, and the system setting isn't touched. Tested on the Thor: turning Lossless
     Scaling on and off (120 Hz with it, with the usual performance; 60 Hz without it), and going to the background and
     back. LARECOMP_VK_MATCH_REFRESH=0: as in 0.7.6 (docs/debug-hooks.md).
  3. The starting lead now depends on the refresh (the GPU, ~12 ms, and 1.25 compositor refreshes: 22.4 ms at 120 Hz,
     32.8 at 60) and is relearned, along with what's normal for the display, when the rate changes.

0.7.0-alfa (2026-11-18) — Lossless Scaling frame generation inside the game
  1. Menu > Video > "Lossless Scaling frame generation": x2, x3 or x4, with "Flow scale (LSFG)" and "Performance mode

     the multiplier (with 120 Hz and x2, 60 real fps, what battles ask for). A bit more latency.

     at 50% 1.2. Memory at 1080p: its own, 43 MB (27 in performance mode, 20 with flow at 50%; the same with x2, x3 or

0.6.0-alfa (2026-11-18) — Snapdragon GSR 2: Qualcomm's temporal anti-aliasing and upscaling
  1. "Anti-aliasing" has a new option: Snapdragon GSR 2 (Snapdragon Game Super Resolution 2, by Qualcomm, 3-clause BSD),
     its 2-pass variant with fragment shaders, the one Qualcomm recommends for mobile. It combines several frames using
     the game's own motion vectors (the same ones AMD FSR uses on PC): stable edges and fine detail. With "GSR 2
     quality" (Quality x1.5, Balanced x1.7, Performance x2, Ultra performance x3) the scene is drawn with fewer pixels
     and GSR 2 upscales it; the UI always stays at full resolution.
  2. Adapted to the port: rendering into the corner of larger images (like FSR's dynamic resolution), URP's reversed
     depth and its motion vectors, the port's subpixel jitter (Halton 2,3 with FSR's phases), and the history in its own
     scene-sized RGBA16F images. From the original, the central 2x2 of depth is taken in Vulkan's textureGather order
     (the original read other rows). From its compute variants: the color is compressed to [0, 1) before blending (the
     scene is HDR; the fragment one is for LDR) and the filter's width is limited to 1.99 (at x3 the weights could add
     up to 0: NaN). With reset, only the current frame.
     Without memory for its images, the whole frame carries on at the low scale and GSR 2 is retried after a while.
     Reviewed by 3 reviewers and a verifier before publishing: those fixes and the menu's came out of that. At x1.5,
     after them, a still image shimmers half as much (0.76 -> 0.38) and looks closer to native.
  3. Tested on PC (the Thor couldn't be used): it looks similar to AMD FSR 3.1, with no trails on moving things; the
     sign of the subpixel jitter, measured (flipping either axis makes a still image shimmer more and lose sharpness);
     0.15 ms of GPU at 1080p on an RX 9070 XT. On the Adreno, estimated from Qualcomm's figure: about 0.65 ms at 1080p.
     On Android, tested in the emulator (x86_64, software Vulkan): GSR 2 turns on at native and at x1.5
     (853x480 -> 1280x720) without errors. Also on PC, as the fourth anti-aliasing option. In larecomp.ini, "antialias =
     gsr2"; for tests, LARECOMP_SET antialias=3 (with fsr_mode), LARECOMP_GSR2_MV and LARECOMP_GSR2_JIT (signs).
  4. Menu: the quality's impact says how many pixels are really drawn, and no longer adds AMD FSR's memory if FSR isn't
     the chosen anti-aliasing (nor the "measured on this PC" on Android); GSR 2's impact estimates its cost on the
     Adreno from Qualcomm's table according to the quality (about 1.2 ms at native 1080p, 0.7 at x2). When switching
     between AMD FSR and GSR 2, the history starts over.
  5. The fade to black in transitions (when entering an area or a house) covers the whole screen when it's wider than
     16:9, like many phones' (20:9): the same as PC's 0.48.1-beta. On the Thor (16:9), no change.

0.4.0-alfa (2026-11-17) — on the Thor: trees without flicker, and the game stops in the background
  1. Trees and foliage that flickered on the Adreno: leaves missing in chunks, or the whole tree bare, on alternate
     frames. URP's depth prepass loses fragments of the alpha-clipped leaf cards on the Adreno 740 (driver 676), and the
     color pass, which draws with EQUAL depth, left those gaps. Verified that it isn't the texture, the sampler, the
     constants, the position (without discards the two passes match), early Z or the vertex shaders' FMAs. On Qualcomm
     GPUs, EQUAL becomes "nearer or equal" without bias, in the direction of the depth (according to its last clear): it
     fills the prepass's gaps and nothing more (without the bias that on PC let the walls draw over the plants right up
     against them). Measured outside Mario's house: the treetops as on PC in every screenshot, and the flicker from
     12.2% of the pixels to 5.3% (what's left is the wind). LARECOMP_VK_EQUAL_TOL=0 turns it off.
  2. In the background (Home, another app) the game stops, as on the Switch, and resumes when you come back: the game's
     threads stop at their next safe point, with the kernel's cooperative pause (the IL2CPP collector's, without
     touching its own pauses). LARECOMP_NO_BG_PAUSE=1: it keeps running. SDL's notifications are handled with an event
     watch: with SDL's block-on-pause, the event loop wouldn't see them until coming back.
  3. For tests: LARECOMP_VK_EQUAL_TOL 1-4, LARECOMP_VK_VS_NOFMA, LARECOMP_VK_DISCARD_FRAGDEPTH; LARECOMP_LOG_TEXFMT also
     logs when a shader gets the empty view.
  Pending: the exact cause of what the prepass loses (it's in the driver).

0.3.0-alfa (2026-11-17) — the AYN Thor: lava room right and at 60 FPS, menu on the Back button, return from background
  1. Tested on the AYN Thor (Snapdragon 8 Gen 2, Adreno 740 with driver 676, Android 13): at 60 FPS at 1080p in Bowser's
     Keep, with its controller ("Odin Controller") and sound.
  2. The lava room in Bowser's Keep (d01f1c), on the Adreno:
     - The lava came out flat, in cracked slabs, and its bubbles green: with dynamic vertex input
       (VK_EXT_vertex_input_dynamic_state) Qualcomm's driver misreads the attributes of some meshes. On Qualcomm GPUs
       the vertex format goes in each pipeline (LARECOMP_VK_DYN_VERTEX=1 makes it dynamic again).
     - A red and black checker pattern (32x16 px blocks) flickered in half of the frames: URP's CopyDepth (two triangles
       that copy the scene's depth with gl_FragDepth to _CameraDepthTexture) left blocks unwritten on the Adreno, and
       the particles that read it (the glow over the lava) came out checkered. It wasn't the synchronization, the format
       (D24S8 / D32S8) or the GENERAL layout. Now that copy is an image copy (vkCmdCopyImage): the same result with less
       work; 0 frames with the pattern out of 53 (~50% before). On by default on Android and on Qualcomm GPUs
       (LARECOMP_VK_COPYDEPTH_XFER=0 / 1).
     - 15 FPS: one of the room's shaders (fs def772159b2635d0) declared 1 KB of local memory per pixel and zeroed it for
       each one: 57 ms per frame on the Adreno (the GPU's private memory). The translator now gives each shader the
       local memory its header asks for (SPH: low + high + CRS stack / 32, like Ryujinx; this one asks for 16 bytes or
       less: 4 words), and grows it if some LDL / STL with a fixed offset goes beyond it. From 69 to 14 ms of GPU per
       frame: 60 FPS (LARECOMP_LMEM_FULL=1: the previous 256 words). It applies to PC too.
  3. More Adreno differences, so that the translated shaders give the same results as on PC:
     - No 64-bit integers in shaders (shaderInt64): the address math, with 32-bit words (LARECOMP_VK_NO_INT64=1 forces
       it on another GPU).
     - SHFL with its bound and segment mask operand (PTX's shfl): the game spreads one value across each quad for its
       derivatives (SHFL + FSWZADD), and before, thread 0 of the whole subgroup was read (on PC, some textures a bit
       blurry).
     - MUFU.SIN / COS with the angle reduced to [-pi, pi] (on the Switch RRO does it; the Adreno can't handle large
       angles: the lava came out black).
     - D24S8 depth (the Switch's) also when D32S8 doesn't support blits. Textures in a format the GPU doesn't filter
       linearly (32-bit floating point, D16), unfiltered; except with comparison (shadows: linear PCF).
     - Every new color target, zeroed (the game counts on clean memory).
     - Coherent memory for each frame's data ring, the readback and the empty buffer (the Adreno also offers cached
       memory that isn't coherent, and nothing flushed it).
  4. Returning from the background: after leaving with Home and coming back, the game stayed black. The Vulkan surface

0.2.0-alfa (2026-11-17) — the APK also carries arm64 (the AYN Thor): the game, moved in memory
  1. On Android arm64 a process's address space is 39 bits (512 GB) and the game's usual window,
     0x70_0000_0000-0x80_0000_0000, is where Android puts its libraries and its memory: there the game goes
     0x60_0000_0000 lower, at 0x10_0000_0000 (runtime/guest_addr.h: GUEST_SHIFT and GADDR). The game's code is generated
     for the moved bases (tools/gen.py <base>) and its functions keep their usual names (gen.py --name-shift), so the
     fixes and the program still find them; the hand-written addresses (rt.h, kernel.h, the GA table, the 38 in
     tools/game_overrides.c and a dozen in the program) go through GADDR. On PC and on x86_64 nothing changes
     (GUEST_SHIFT 0).
  2. The game's code for arm64 (generated-aarch64, with ARM's vector instructions: gen.py --simd asm): a 203 MB
     lasgame.so, 154,122 + 39,483 functions.
  3. A single APK with both architectures, arm64-v8a and x86_64 (tools/android/apk.sh, whichever are built).
  4. Tested in the emulator running the ARM version (the emulator translates the ARM code to x86): the game loaded at
     0x1000000000, title, loading a save and playing in Bowser's Keep, with the picture the same as on PC.
  5. runtime/platform/android.c: if the game's code doesn't come with a .cpu (the arm64 one doesn't have it), the one in
     the internal folder is deleted (an old x86_64 one would have rejected it).
